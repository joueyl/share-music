# 协议与实现入口

服务端权威状态在 `apps/server/src/engine.ts`，WebSocket 接入在 `gateway.ts`。客户端连接与命令由 `apps/client/src/bridge.ts` 管理。

## 控制

WebSocket `/ws` 建立后 5 秒内发送 `auth` 与 token；成功后发送 `join`。单账号同时只保留一条控制连接。音源加载与 ready 上报绑定当前房间和播放代次。

命令消息为 `{type:"command",data:{commandId,roomId,expectedStateVersion,action:{type,payload}}}`。服务端依次鉴权、版本检查和去重，冲突返回快照。操作名与严格 payload 由 `packages/shared/src/index.ts` 定义。“播放列表控制”沿用 enqueue 布尔字段，统一管理添加、删除、排序及清空，取消旧的独立“加入播放列表”权限。成员可按房间默认或单独覆盖授权，新房间默认权限全开，已保存设置不自动修改。clear 保留当前歌曲（含暂停），无当前歌曲时全清空；pending 期间拒绝清空以保护准备中的音轨。播放权限仍独立校验。需要同步更新服务端和客户端以使用新的权限语义，无数据库结构迁移。

`pending` 包含旧播放状态、准备代次、ready 成员、5 秒截止时间与 committed 标志。所有在线成员准备完成或超时后公布生效时间；最少保留 200ms 提交窗口。暂停与音质切换按最终生效时间从旧时间轴重算位置，seek 使用请求位置。

客户端发送 clock 消息测量往返；采用低延迟样本估计服务器偏移，渲染时本地计算锚点后的进度。服务端快照始终是权威状态。

## 房间播放模式

快照顶层 playbackMode 和 playbackMode 命令统一房间模式：queue 点歌、shuffle 随机、single 单曲循环、loop 列表循环。命令 payload 为 `{mode}`，使用独立 permissions.playbackMode 布尔权限（播放模式修改），不再依赖 skip 或 enqueue；支持房间默认及成员覆盖。沿用 expectedStateVersion、commandId、确认回执及持久化；pending 期间禁用切换。准备/提交及唯一 Audio 时间轴不变，不能使用本地 Audio.loop 代替服务端决定下一曲。

自然结束由服务端 tick 判断：点歌模式删除已完成曲并持久化，其他模式不删除；随机只在实际提交播放后将歌曲记入本轮已播集合，排序/普通快照/暂停/seek 不重置轮次，播放准备失败不算已播。全部可播放曲已播后开启新一轮，多首时避免跨轮立即重播上一曲；新添加歌曲可进入当前轮，删除及离线曲不阻塞可播放集合。手动点播和上一首允许主动回听。单曲循环也经过新的准备/ready/提交代次，不由客户端擅自重播。

模式持久化；未保存模式的旧房间默认点歌（播完删曲），服务重启清除播放与随机轮次。必须同步更新前后端；旧快照缺少模式字段时客户端禁用入口，无数据库结构迁移。

## 房间聊天与生产部署检查

聊天流也包含服务端生成的操作记录（`ChatMessage.kind: "activity"`）。记录带服务端确认的操作者、时间和歌曲名称，包括点播、上一首/下一首、暂停/继续、停止、拖动进度（`mm:ss`）、添加/移除歌曲、清空/排序和音质调整。客户端以轻量提示行与普通聊天按顺序混排，沿用滚动、未读提示和加入房间历史。

记录表示操作已被服务端接受；播放类操作仍需后续音源准备和同步，不保证音频已实际发声。失败/无权限/版本冲突的操作、命令重试、自动进度上报及后台同步不会产生记录。记录与聊天共享最近 100 条进程内历史，重启后清空，仅同房间可见；必须同时更新服务端才能生成记录。

客户端通过同一条 `/ws` 发送 `{type:"chat",roomId,requestId,text}`，`requestId` 为 UUID。
服务端保存消息后向发送者返回 `{type:"chat-result",requestId,data}`，再向房内广播 `{type:"chat",data}`；失败返回 `{type:"chat-error",requestId,error}`。
客户端兼容旧版仅广播的成功确认；收到旧服务端 `UNKNOWN_MESSAGE` 时提示更新服务端。
相同用户、相同 requestId 的重试在最近 100 条历史范围内返回原消息，不重复广播；超时只代表未确认，并不保证消息未发送。

生产环境必须同步更新服务端与客户端，不能只重新打包桌面客户端。
使用仓库提供的 Compose 部署时，在仓库根目录执行 `docker compose -f deploy/compose.yml up -d --build api`，保留现有数据卷，不要使用 `down -v`。
更新后检查 `/api/health` 返回 `chatProtocolVersion: 1`，再让客户端重新连接。
缺少该字段只能说明未部署本次回执版本，不能单独据此判定旧服务端是否支持聊天。
若经负载均衡部署了多个实例，当前房间状态与聊天历史均在进程内，不能无状态地跨实例分发同一房间的连接。

## 音源加载与播放

客户端 `bridge.ts` 管理 HTTP、WebSocket 与唯一播放器，`cloud-player.ts` 控制 HTML Audio；Rust `apps/client/src-tauri/src/music_cache.rs` 和 `playback_audio.rs` 提供桌面下载、完整性校验与缓存。

客户端通过受权限保护的音乐接口取得音源：桌面下载 HTTPS 网易云或 QQ 音乐白名单 CDN 原始字节，浏览器使用 `/api/rooms/:id/music/:trackId/audio`。下载限制为 100 MiB，前端计算 MD5 并比对接口值和文件大小后创建 Blob；下载失败或不一致时自动强制刷新直链与配套摘要、大小并重新下载校验一次，成功后继续播放；桌面缓存同样校验。网易云后端只从接口保存 MD5 和大小，不为导入或续链下载音频；QQ 上游不提供 MD5，服务端限时、限量读取完整 128K MP3 计算 MD5 与实际大小，不持久化音频；网页音频代理仅做有界下载和权限检查。接口和链接刷新策略见 [API](API.md) 与 [音乐来源说明](MUSIC-SEARCH.md)。

播放器等待目标位置 seek 完成且 buffered 后报告 ready，服务端提交生效时间后按共享时间轴播放、暂停和纠偏。房间、歌曲或播放代次切换后忽略过期下载与异步结果；换歌和离房释放内存 Blob，桌面磁盘缓存按内容哈希复用。本地音量不影响其他成员。

独立模式权限兼容：新房间默认开启；旧房间无 defaults.playbackMode 时按旧 defaults.skip 补齐，旧成员存在 skip 覆盖且未设模式权限时迁移其原有效权限，避免升级自动提权。已有独立字段后，成员未设置则跟随房间，不再随 skip 改变。旧 defaults 请求省略新增字段时保留现值；无需数据库结构迁移，权限沿用 defaults/overrides JSON 持久化，需同步更新前后端。

## 网易云后台打卡触发

服务端只在新的歌曲播放代次经过 ready/提交后实际生效且房间仍有在线成员时入队打卡；不等待 HTTP 上游响应，也不在 enqueue、准备或取消时提交。按用户配置要求，播放中上报歌曲整首总时长而非实测收听时长。暂停、继续、seek 和音质同步虽然会更新 sourceEpoch，但不视为新的歌曲播放，不重复上报；切歌、立即播放及自然循环的新歌曲开始可入队。观察者失败不能中断房间 tick；单并发有界队列、凭据隔离与每日任务规则见 [NETEASE.md](NETEASE.md#服务端每日任务与播放打卡)。不改变 WebSocket 消息形状或客户端播放权限。
